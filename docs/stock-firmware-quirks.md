# Observed firmware quirks (in the stock firmware built with the vendor AppoTech SDK)

The notes below distinguish the asset behavior reproduced during this work from other owner-reported menu and USB behavior. The latter have not yet been independently traced at the file-system or USB-command level.

| Area | Observed behavior | Evidence and limits |
|---|---|---|
| JPEG asset decoding | An initial overlay replacement rendered as [garbled content](failed-garbled-overlay-replacement.jpg). A revised 640×480 JPEG rendered correctly after matching the stock asset's baseline encoding, 4:2:0 chroma sampling, quality 80, and exact 25,490-byte slot boundary. | Reproduced in the asset experiment and confirmed in [`successful-overlay-replacement.jpg`](successful-overlay-replacement.jpg). Several JPEG details changed between attempts, so the particular parser constraint is not isolated. The camera appears sensitive to JPEG encoding or resource layout beyond dimensions alone. |
| SD-card format menu | Formatting is intermittent: sometimes pressing OK exits the format dialog without formatting; on other attempts the format completes successfully. | Owner-reported. The success/failure conditions have not been isolated, and no card-state or storage trace has been captured. |
| USB mass-storage disconnect | After connecting the camera to a computer so it enters mass-storage (MSC) mode, unplugging USB turns the camera off, according to the owner. | The power off does not happen after a safe eject from a PC, it only happens after a USB disconnect. Normal power on (with USB data disconnected) still works as usual and the camera still responds to holding the power button while in MSC mode or during normal operation.|
| Delete of internal-flash images | The UI marks the image as deleted, but the image payload remains in SPI flash. | Owner-reported from SPI inspection. This suggests logical deletion or an index update without physical erasure; the metadata update and exact payload boundaries have not been mapped. The UART boot log names the store: `udisk_addr=0x1ba000`, `udisk_capacity=0x45000`, `pic_max_num=6`, header `sizeof(spi_udisk_head)=0xfb0`. In dumps that still hold a JPEG at `0x1bb000` the head reads `pic_num=0`, which fits deletion by bookkeeping only. |
| Sys. Reset (factory reset) | The menu's Sys. Reset option resets the saved settings only. It does not remove user-saved JPEGs, which stay in the internal flash photo store (`0x1bb000` onward) exactly as after a normal delete. | Owner-reported; the flash was not diffed before and after a reset. It is consistent with the delete quirk above (images are only ever unlisted, never erased), but nothing shows what the reset does write. A factory reset therefore does not make a camera safe to dump or hand over. |
| Non-erased photo area | A flash image whose photo area `0x1bb000..0x1fffff` was blanked with `0x00` (stock free space `0x1c0000..0x1fffff` is `0xff`; the photo slots are mostly zeros around the photo data) booted to the stock logo and USB mass-storage mode, but reset itself a few seconds after its first start. A manual reset then started it normally and it did not repeat. The same area padded with `0xff` booted on its first start without a reset and stayed up. | Owner-observed once per variant, 2026-10-17, flashed and rebooted the same way (SDK `system reboot` into the stock firmware). The UART log up to the reset is a normal start (`spi_udisk_init ok`, `pic_num=0`), so the stock firmware does not report a fault. Owner's hypothesis: the firmware tried to reset the unexpected area and soft-rebooted once. Not proven: one run each, and `0x00` versus `0xff` is the only intended difference. |

These observations describe visible behavior, not confirmed root causes. In particular, the JPEG experiment shows that a compatible replacement can render, but it does not identify which JPEG field or padding rule the firmware requires.
